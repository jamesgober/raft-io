# raft-io v1.2.0

**Safety release. Upgrade every node.**

An independent review in 2026-11 found that a newly elected leader could
start a membership change before committing anything in its own term, the
single-server change hazard Diego Ongaro described on raft-dev in 2015. In
rare schedules that lets two different entries commit at the same index.
1.2.0 fixes it the standard way and fixes the other findings of the same
review.

## What changed

- Every leader appends an election no-op (a configuration entry re-asserting
  the current membership), and a membership change returns
  `ConfigInProgress` until an entry of the leader's own term has committed.
  One configuration change may be uncommitted at a time, as before.
- The no-op carries learners as well as voters, so learners survive leader
  changes.
- A follower's commit index and applied index never move backwards, and an
  older snapshot is ignored instead of rolling applied state back.
- A leadership transfer that has not completed within one maximum election
  timeout is abandoned. While it is pending, proposals and membership changes
  return the new `Error::TransferInProgress { target }`.
- `WalLog` rewrites its file when a snapshot is installed, keeping only the
  snapshot, the live entries above it and the hard state.
- A sent snapshot is not resent until its reply arrives or two maximum
  election timeouts pass.
- Replies, votes and appends from faulty peers are checked before use.
- `framing::decode` accepts only canonical encodings and caps decode memory at
  16 MiB or twice the frame length; `framing::decode_with_config` sets a fixed
  cap.
- Commit advancement is a quorum select over the voters' match indexes.
- `pack-io` moves to 2.1.

## Visible behaviour

- The first entry a new cluster applies is index 2 (index 1 is the no-op).
  Applied indexes were already strictly increasing but not contiguous.
- A membership change requested in the first round trip after an election is
  refused with `ConfigInProgress`; retry it.
- During a leadership transfer, proposals get `TransferInProgress` instead of
  `NotLeader` naming the leader itself.

## Compatibility

No wire or disk format changes. The no-op is an ordinary configuration entry,
byte-identical to 1.1 when there are no learners; with learners it uses the
learner section 1.0 and 1.1 already read. `WalLog` files from 1.0 and 1.1 open
unchanged, and a 1.1 node can read a file 1.2 compacted. Nodes on 1.0, 1.1 and
1.2 interoperate, so a rolling upgrade works. The membership fix protects a
term only when its leader runs 1.2: finish the upgrade before making
membership changes, or make them only while a 1.2 node leads.

## Verification

`tests/regressions.rs` holds a deterministic schedule for each fix, each of
which fails on 1.1.0. `tests/simulation.rs` runs a seeded cluster simulation
(crash-restart on a log that loses unsynced writes, partitions, message loss,
reordering and duplication, membership churn including an isolated leader
holding an uncommitted change, transfers, snapshots, reads) and checks
election safety, log matching, leader completeness, state machine safety and
monotonic commit and apply indexes.

## Not changed

- `RaftTransport` is still an optional helper that the node never calls; the
  docs now say so. A driver that routes `Action::Send` through it may come in
  a later minor.
- `RaftLog::snapshot` still returns an owned snapshot, so a send clones the
  data once; sharing it by reference needs a trait change and waits for 2.0.
